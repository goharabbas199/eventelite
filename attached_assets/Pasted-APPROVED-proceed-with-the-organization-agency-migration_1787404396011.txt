Child records may inherit organization ownership through their parent rather than receiving organizationId directly.

Before applying NOT NULL constraints or foreign keys, perform explicit data verification.

IMPORTANT:
Do not delete or automatically repair orphaned records.

If orphaned records exist, report them and preserve them.

STEP 2 — CREATE ORGANIZATION

Create the organizations table using the approved structure:

id
name
createdAt
updatedAt

Create exactly ONE default organization for the current existing dataset.

Use a clear name based on the application's existing company/application identity if that is already available.

Do not invent sensitive or inaccurate company information.

STEP 3 — BACKFILL

Add nullable organization_id fields first to:

users
clients
events
vendors
venues
quotations
invoices
app_settings

Backfill every existing record to the default organization.

Verify counts before and after backfill.

Do not lose any records.

STEP 4 — SETTINGS

Change app_settings from:

PRIMARY KEY (key)

to:

PRIMARY KEY (organization_id, key)

Preserve the existing settings values.

Do not create duplicate settings rows.

STEP 5 — FOREIGN KEYS

After successful backfill and verification:

Add foreign keys:

users.organization_id → organizations.id
clients.organization_id → organizations.id
events.organization_id → organizations.id
vendors.organization_id → organizations.id
venues.organization_id → organizations.id
quotations.organization_id → organizations.id
invoices.organization_id → organizations.id
app_settings.organization_id → organizations.id

Use appropriate ON DELETE behavior.

Do NOT cascade-delete entire business datasets when an organization is accidentally deleted.

Prefer RESTRICT/NO ACTION for organization deletion unless the application already has an explicit safe organization-deletion workflow.

STEP 6 — NOT NULL

Only after verifying:

- zero NULL organization IDs
- every organization ID references the default organization
- all existing records remain present

change organization_id to NOT NULL.

STEP 7 — INDEXES

Add indexes to organization_id fields.

Also consider composite indexes where they materially improve common organization-scoped queries.

Do not create excessive indexes.

STEP 8 — ORM

Update Drizzle schema and relations to represent:

Organization
→ Users
→ Clients
→ Events
→ Vendors
→ Venues
→ Quotations
→ Invoices
→ App Settings

Do not remove existing relationships.

STEP 9 — REQUEST CONTEXT

Use the authenticated server-side user's organizationId.

NEVER trust organizationId supplied by the browser.

For every aggregate-root query:

SELECT/UPDATE/DELETE must be scoped to the authenticated organization.

For child records:
- verify parent belongs to current organization
- prevent cross-organization relationships
- return normal not-found behavior for inaccessible records

Especially verify:

vendor payments:
client.organizationId === vendor.organizationId === currentUser.organizationId

quotations:
quotation.organizationId === currentUser.organizationId
and optional client/venue must belong to same organization

events:
event.organizationId === currentUser.organizationId
and client/venue must belong to same organization
